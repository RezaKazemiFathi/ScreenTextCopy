## ۰. پیش از شروع

سه چیز لازم دارید:

| مورد | توضیح |
|---|---|
| یک حساب گیت‌هاب | رایگان است. در مرحلهٔ ۳ می‌سازیمش. |
| گیت روی ویندوز | ابزار خط فرمانی که فایل‌ها را به گیت‌هاب می‌فرستد. مرحلهٔ ۱. |
| پوشهٔ آمادهٔ پروژه | همان پوشهٔ `Github` که همهٔ فایل‌های نهایی داخلش است. |

**یک نکتهٔ مفهومی که همه‌چیز را ساده می‌کند:** گیت و گیت‌هاب دو چیز جدا هستند. *گیت*
برنامه‌ای است روی رایانهٔ شما که تاریخچهٔ تغییرات کدتان را نگه می‌دارد. *گیت‌هاب* یک
سایت است که یک کپی از آن تاریخچه را روی اینترنت میزبانی می‌کند. کارِ همیشگی این است:
تغییر می‌دهید ← در گیت **commit** می‌کنید ← به گیت‌هاب **push** می‌کنید.

## ۱. نصب گیت روی ویندوز

پاورشل را باز کنید (کلید ویندوز را بزنید، `powershell` را تایپ کنید، Enter) و اول
ببینید آیا گیت از قبل نصب است:

</div>

```powershell
git --version
```

<div dir="rtl">

اگر چیزی مثل `git version 2.54.0.windows.1` دیدید، نصب است و می‌توانید به مرحلهٔ ۲
بروید. اگر خطای «not recognized» گرفتید، نصبش کنید:

</div>

```powershell
winget install --id Git.Git --accept-package-agreements --accept-source-agreements
```

<div dir="rtl">

بعد از پایان نصب، **پاورشل را ببندید و یک پنجرهٔ جدید باز کنید** (تا مسیر جدید شناخته
شود) و دوباره `git --version` را بزنید.

> اگر `winget` را ندارید، نصب‌کنندهٔ گیت را از [git-scm.com](https://git-scm.com/download/win)
> دانلود کنید و در ویزارد همهٔ گزینه‌های پیش‌فرض را بپذیرید. یکی از آن پیش‌فرض‌ها
> **Git Credential Manager** است که در مرحلهٔ ۶ ورودتان به گیت‌هاب را انجام می‌دهد، پس
> تیکش را برندارید.

## ۲. معرفی خودتان به گیت

گیت نام و ایمیل شما را روی هر کامیت ثبت می‌کند. این کار **یک‌بار برای همیشه** انجام
می‌شود:

</div>

```powershell
git config --global user.name "Reza Kazemi Fathi"
git config --global user.email "you@example.com"

# نام شاخهٔ اصلی در پروژه‌های جدید main باشد (پیش‌فرض قدیمی master بود).
git config --global init.defaultBranch main
```

<div dir="rtl">

**ایمیل مهم است:** اگر ایمیلی بنویسید که در حساب گیت‌هابتان ثبت نشده باشد، کامیت‌ها به
پروفایلتان وصل نمی‌شوند و در نمودار فعالیت دیده نمی‌شوند. همان ایمیلی را بنویسید که با
آن در گیت‌هاب ثبت‌نام می‌کنید. اگر نمی‌خواهید ایمیل واقعی‌تان عمومی شود، گیت‌هاب یک
ایمیل مخصوص به شما می‌دهد به شکل `<id>+<username>@users.noreply.github.com` که در
**Settings → Emails** قابل مشاهده است و می‌توانید همان را اینجا بگذارید.

برای دیدن تنظیمات ثبت‌شده:

</div>

```powershell
git config --global --list
```

## ۳. ساختن حساب و مخزن در گیت‌هاب

### ۳.۱ ساختن حساب

اگر حساب ندارید: به [github.com/signup](https://github.com/signup) بروید، ایمیل و رمز و
نام کاربری بدهید، و ایمیلتان را تأیید کنید. نام کاربری در آدرس همهٔ پروژه‌هایتان دیده
می‌شود، پس چیزی حرفه‌ای انتخاب کنید (مثلاً `rezakazemifathi`).

### ۳.۲ ساختن مخزن (repository)

۱. بالا سمت راست روی علامت **+** بزنید و **New repository** را انتخاب کنید.
۲. فیلدها را این‌طور پر کنید:

| فیلد | مقدار |
|---|---|
| Repository name | `ScreenTextCopy` |
| Description | `Grab text from anywhere on your Windows screen — offline OCR, AI translation, send to phone.` |
| Public / Private | **Public** (تا دیگران ببینند و دانلود کنند) |
| Add a README file | ❌ تیک نزنید |
| Add .gitignore | ❌ تیک نزنید |
| Choose a license | ❌ انتخاب نکنید |

سه گزینهٔ آخر را تیک نمی‌زنیم چون پوشهٔ محلی شما همین حالا `README.md` و `.gitignore` و
`LICENSE` دارد. اگر گیت‌هاب هم نسخهٔ خودش را بسازد، در اولین push تضاد (conflict) پیش
می‌آید و کار بی‌دلیل سخت می‌شود.

۳. **Create repository** را بزنید.

صفحه‌ای که می‌بینید چند دستور پیشنهادی نشان می‌دهد. لازم نیست از آن‌ها استفاده کنید —
مراحل بعدی همین راهنما دقیقاً همان کار را با توضیح انجام می‌دهد. فقط آدرس نمایش‌داده‌شده
را یادداشت کنید:
`https://github.com/<نام-کاربری-شما>/ScreenTextCopy.git`

## ۴. آماده‌سازی پوشهٔ محلی

در پاورشل وارد پوشهٔ آمادهٔ پروژه شوید:

</div>

```powershell
cd E:\Prog\ScreenTextCopy_MVP\Github
```

<div dir="rtl">

بعد این پوشه را به یک مخزن گیت تبدیل کنید:

</div>

```powershell
git init
```

<div dir="rtl">

خروجی چیزی شبیه `Initialized empty Git repository in .../Github/.git/` است. از این لحظه
یک پوشهٔ مخفی `.git` ساخته شده که تاریخچه در آن نگه داشته می‌شود. **هرگز آن را دستی پاک
یا ویرایش نکنید.**

حالا ببینید گیت چه چیزهایی را می‌بیند:

</div>

```powershell
git status
```

<div dir="rtl">

فهرست بلندی از فایل‌های «Untracked» می‌بینید. یک بررسی مهم: **مطمئن شوید پوشهٔ
`src/ScreenTextCopy/Tesseract/` در این فهرست نیست.** فایل `.gitignore` این پوشه را
عمداً کنار گذاشته، چون یکی از فایل‌هایش (`libtesseract-5.dll`) حدود ۱۰۶ مگابایت است و
گیت‌هاب سقف سختِ ۱۰۰ مگابایت برای هر فایل دارد؛ اگر کامیت شود، push شما رد می‌شود.

برای بررسی قطعی:

</div>

```powershell
# باید هیچ خروجی‌ای نداشته باشد؛ یعنی هیچ فایل Tesseract در صف کامیت نیست.
git status --porcelain | Select-String "Tesseract"

# و این نشان می‌دهد کدام قاعده آن مسیر را نادیده گرفته است.
git check-ignore -v src/ScreenTextCopy/Tesseract/tesseract.exe
```

<div dir="rtl">

دومی باید چیزی مثل این چاپ کند:
`.gitignore:20:src/ScreenTextCopy/Tesseract/ src/ScreenTextCopy/Tesseract/tesseract.exe`

اگر خروجی اولی خالی نبود، یعنی `.gitignore` سر جایش نیست — قبل از ادامه دادن آن را درست
کنید.

</div>

## ۵. اولین کامیت

کامیت در دو گام انجام می‌شود: اول فایل‌ها را «صحنه‌آرایی» (stage) می‌کنید، بعد ثبتشان
می‌کنید.

</div>

```powershell
# همهٔ فایل‌هایی که .gitignore منعشان نکرده را به صف کامیت اضافه کن.
git add .

# ببین دقیقاً چه چیزی در صف است.
git status
```

<div dir="rtl">

حالا فایل‌ها با رنگ سبز و عنوان «Changes to be committed» نمایش داده می‌شوند. یک نگاه
دقیق به این فهرست بیندازید؛ این آخرین فرصت راحت برای جلوگیری از کامیت شدنِ چیزی است که
نباید عمومی شود.

اگر همه‌چیز درست بود، ثبتش کنید:

</div>

```powershell
git commit -m "feat: initial public release of ScreenTextCopy 2.0.0"
```

<div dir="rtl">

خروجی تعداد فایل‌ها و خطوط اضافه‌شده را نشان می‌دهد. اگر هشدارهایی مثل
`LF will be replaced by CRLF` دیدید نگران نباشید — این کار عمدی است و فایل `.gitattributes`
پروژه آن را مدیریت می‌کند.

اگر پیام `Please tell me who you are` گرفتید، مرحلهٔ ۲ را انجام نداده‌اید.

### چرا پیام کامیت این شکلی است؟

این پروژه از قاعدهٔ **Conventional Commits** استفاده می‌کند: پیام با نوع تغییر شروع
می‌شود.

| پیشوند | برای چه |
|---|---|
| `feat:` | ویژگی جدید |
| `fix:` | رفع باگ |
| `docs:` | فقط تغییر مستندات |
| `chore:` | کارهای جانبی مثل به‌روزرسانی ابزارها |
| `refactor:` | بازنویسی بدون تغییر رفتار |

## ۶. اتصال به گیت‌هاب و اولین push

سه دستور، به همین ترتیب. در دستور اول `<نام-کاربری-شما>` را با نام کاربری واقعی‌تان
عوض کنید:

</div>

```powershell
# 1) به گیت بگو مخزن راه دور (remote) کجاست. "origin" نام قراردادی آن است.
git remote add origin https://github.com/<نام-کاربری-شما>/ScreenTextCopy.git

# 2) نام شاخهٔ محلی را main بگذار (اگر از قبل main نیست).
git branch -M main

# 3) بفرست. سوییچ -u باعث می‌شود از این به بعد فقط "git push" کافی باشد.
git push -u origin main
```

<div dir="rtl">

**در همین لحظه یک پنجرهٔ ورود باز می‌شود** (Git Credential Manager). روی
**Sign in with your browser** بزنید، در مرورگر وارد حساب گیت‌هابتان شوید و دسترسی را
تأیید کنید. این کار فقط یک‌بار لازم است؛ بعد از آن اطلاعات ورود در Windows Credential
Manager ذخیره می‌شود.

> **رمز حساب گیت‌هاب را در خط فرمان تایپ نکنید.** گیت‌هاب از سال ۲۰۲۱ ورود با رمز را
> برای گیت حذف کرده است. اگر پنجرهٔ ورود مرورگری باز نشد، به‌جای رمز باید یک
> **Personal Access Token** بسازید: در گیت‌هاب به
> **Settings → Developer settings → Personal access tokens → Tokens (classic)** بروید،
> **Generate new token** را بزنید، دسترسی `repo` را بدهید، و توکن ساخته‌شده را به‌جای رمز
> وارد کنید. توکن مثل رمز است — جایی منتشرش نکنید.

بعد از پایان push، صفحهٔ مخزن را در مرورگر باز کنید (`F5` بزنید). باید همهٔ فایل‌ها و
README رندرشده را ببینید.

### بررسی این‌که همه‌چیز رفته

</div>

```powershell
git log --oneline
git remote -v
```

## ۷. مرتب کردن ظاهر مخزن

این‌ها چند دقیقه وقت می‌گیرند و تفاوت بین «یک پوشهٔ کد» و «یک پروژهٔ حرفه‌ای» را
می‌سازند. همه در خودِ سایت گیت‌هاب انجام می‌شوند.

| کار | مسیر | چه چیزی وارد کنید |
|---|---|---|
| توضیح و موضوع‌ها | صفحهٔ اصلی مخزن ← چرخ‌دنده کنار **About** | Description را بنویسید و در Topics این‌ها را اضافه کنید: `ocr`، `screenshot-ocr`، `tesseract`، `wpf`، `dotnet`، `csharp`، `translation`، `persian`، `windows` |
| فعال کردن Discussions | **Settings → General → Features** ← تیک **Discussions** | لینک «پرسش و ایده» در قالب ایشوها به همین بخش اشاره می‌کند |
| دکمهٔ حمایت | **Settings → General → Features** ← تیک **Sponsorships** | فایل `.github/FUNDING.yml` از قبل آماده است و لینک‌ها را نشان می‌دهد |
| گزارش خصوصی آسیب‌پذیری | **Settings → Advanced Security** ← فعال کردن **Private vulnerability reporting** | لینک موجود در `SECURITY.md` را کار می‌اندازد |
| اجازهٔ اجرای Actions | **Settings → Actions → General** | حالت پیش‌فرض کافی است؛ فقط مطمئن شوید Actions غیرفعال نشده باشد |

بعد از فعال شدن Actions، به تب **Actions** بروید؛ ورک‌فلوی `Build` باید همان push اول را
بیلد کرده باشد. اگر سبز شد، نشان (badge) بالای README هم سبز می‌شود.

## ۸. ساختن فایل‌های نصب

کاربر عادی سورس‌کد را کامپایل نمی‌کند؛ او یک فایل نصب می‌خواهد. این فایل‌ها با یک
اسکریپت ساخته می‌شوند:

</div>

```powershell
cd E:\Prog\ScreenTextCopy_MVP\Github
powershell -ExecutionPolicy Bypass -File scripts\build-release.ps1 -Version 2.0.0
```

<div dir="rtl">

اسکریپت پنج کار می‌کند: محیط بیلد را بررسی می‌کند، برنامه را به‌صورت **خودبسنده**
(self-contained) publish می‌کند، کامل بودن بسته را بازبینی می‌کند، فایل zip پرتابل را
می‌سازد و در آخر نصب‌کننده را با Inno Setup می‌سازد. نتیجه در پوشهٔ `release\`:

| فایل | برای کیست |
|---|---|
| `ScreenTextCopy-Setup-2.0.0-win-x64.exe` | کاربر عادی؛ نصب یک‌کلیکی بدون رمز مدیر |
| `ScreenTextCopy-2.0.0-win-x64-portable.zip` | کسی که نصب نمی‌خواهد یا از فلش اجرا می‌کند |
| `SHA256SUMS.txt` | برای بررسی صحت فایل دانلودی |
| `app\` | خروجی خام؛ **آپلود نمی‌شود** |

«خودبسنده» یعنی رانتایم .NET 8 و موتور OCR یعنی Tesseract داخل خود بسته هستند. به همین
دلیل کاربر شما **هیچ پیش‌نیازی نصب نمی‌کند** — نه .NET، نه Tesseract، نه Visual C++.
هزینه‌اش حجم بیشتر فایل نصب است که معاملهٔ درستی است.

اگر Inno Setup نصب نباشد، اسکریپت هشدار می‌دهد و فقط zip پرتابل را می‌سازد. برای نصبش:

</div>

```powershell
winget install --id JRSoftware.InnoSetup
```

<div dir="rtl">

> **پوشهٔ `release\` هرگز کامیت نمی‌شود.** فایل `.gitignore` آن را کنار گذاشته است، چون
> حجم این فایل‌ها از سقف گیت‌هاب برای فایل‌های مخزن عبور می‌کند. جای درست آن‌ها بخش
> Releases است که سقف هر فایل ۲ گیگابایت است.

</div>

## ۹. انتشار نسخه (Release)

### گام ۹.۱ — برچسب نسخه (tag)

یک tag در گیت به معنای «این کامیت، همان نسخهٔ ۲.۰.۰ است»:

</div>

```powershell
git tag -a v2.0.0 -m "ScreenTextCopy 2.0.0"
git push origin v2.0.0
```

<div dir="rtl">

**فرمت نام tag مهم است**: باید با `v` شروع شود، چون ورک‌فلوی
`.github/workflows/release.yml` فقط با tag های `v*` اجرا می‌شود.

### گام ۹.۲ — انتشار خودکار (روش پیشنهادی)

به‌محض push شدن tag، به تب **Actions** بروید. ورک‌فلوی `Release` شروع به کار می‌کند،
خودش Tesseract و Inno Setup را روی سرور گیت‌هاب نصب می‌کند، فایل‌ها را می‌سازد، و یک
Release با هر سه فایل و توضیحات آماده منتشر می‌کند. حدود ۱۰ تا ۱۵ دقیقه طول می‌کشد.

بعد از سبز شدن، به تب **Releases** بروید و نتیجه را ببینید.

### گام ۹.۳ — انتشار دستی (اگر ورک‌فلو شکست خورد)

۱. در صفحهٔ مخزن به **Releases** بروید و **Draft a new release** را بزنید.
۲. در **Choose a tag** همان `v2.0.0` را انتخاب کنید.
۳. عنوان: `ScreenTextCopy 2.0.0`
۴. در بخش توضیحات، خلاصهٔ `CHANGELOG.md` را بگذارید و بنویسید که هیچ پیش‌نیازی لازم نیست.
۵. سه فایل زیر را از پوشهٔ `release\` **بکشید و رها کنید** در ناحیهٔ
   *Attach binaries*:
   `ScreenTextCopy-Setup-2.0.0-win-x64.exe` ·
   `ScreenTextCopy-2.0.0-win-x64-portable.zip` · `SHA256SUMS.txt`
۶. صبر کنید تا آپلود هر سه به ۱۰۰٪ برسد (نوار پیشرفت هر فایل)، سپس
   **Publish release** را بزنید.

از این لحظه لینک «دانلود نصب‌کننده» در README کار می‌کند، چون به
`releases/latest` اشاره می‌کند.

> **دربارهٔ هشدار SmartScreen:** این بیلدها امضای دیجیتال (code signing) ندارند، پس
> ویندوز به کاربر می‌گوید ناشر ناشناس است. این طبیعی است و در `README` و راهنمای نصب
> توضیح داده شده. حذف کامل این هشدار به یک گواهی امضای کد پول‌دار نیاز دارد؛
> `SHA256SUMS.txt` جایگزین رایگان و صادقانهٔ آن برای بررسی صحت فایل است.

<div dir="rtl">

### انتشار نسخهٔ جدید

۱. در `CHANGELOG.md` بخش جدیدی برای نسخه بسازید و تغییرات را زیر Added / Changed / Fixed
   بنویسید.
۲. کامیت و push کنید.
۳. فایل‌های نصب را با شمارهٔ نسخهٔ جدید بسازید:
   `powershell -ExecutionPolicy Bypass -File scripts\build-release.ps1 -Version 2.1.0`
۴. tag بزنید و push کنید: `git tag -a v2.1.0 -m "ScreenTextCopy 2.1.0"` و
   `git push origin v2.1.0`

شمارهٔ نسخه از قاعدهٔ **Semantic Versioning** پیروی می‌کند: `2.1.0` ← عدد سوم برای رفع
باگ، عدد دوم برای ویژگی جدید، عدد اول برای تغییری که سازگاری را می‌شکند.

> کاربرانی که نسخهٔ قبلی را نصب کرده‌اند، با اجرای نصب‌کنندهٔ جدید ارتقا می‌گیرند و
> تنظیماتشان حفظ می‌شود؛ شناسهٔ `AppId` در فایل نصب‌کننده ثابت مانده تا نصب جدید روی
> نصب قبلی بیفتد، نه کنارش.

## ۱۱. خطاهای رایج و راه‌حلشان

| پیام خطا | معنی و راه‌حل |
|---|---|
| `src refspec main does not match any` | هنوز هیچ کامیتی نساخته‌اید. مرحلهٔ ۵ را انجام دهید. |
| `failed to push some refs` / `Updates were rejected` | مخزن گیت‌هاب کامیتی دارد که شما ندارید (مثلاً README که موقع ساخت مخزن تیک زده‌اید). با `git pull --rebase origin main` آن را بگیرید، بعد `git push`. |
| `remote: error: File ... is 106.10 MB; this exceeds GitHub's file size limit of 100.00 MB` | یک فایل بزرگ (تقریباً همیشه `libtesseract-5.dll`) کامیت شده. با `git rm --cached -r src/ScreenTextCopy/Tesseract` از صف خارجش کنید، مطمئن شوید `.gitignore` درست است، و کامیت را با `git commit --amend` اصلاح کنید. |
| `Support for password authentication was removed` | با رمز حساب وارد شده‌اید. مرحلهٔ ۶ و بخش Personal Access Token را ببینید. |
| `fatal: not a git repository` | در پوشهٔ درستی نیستید. `cd E:\Prog\ScreenTextCopy_MVP\Github` را بزنید. |
| `Please tell me who you are` | مرحلهٔ ۲ انجام نشده است. |
| `remote origin already exists` | قبلاً remote را اضافه کرده‌اید. برای اصلاح آدرس: `git remote set-url origin <آدرس-درست>`. |
| `LF will be replaced by CRLF` | هشدار است، نه خطا. `.gitattributes` این تبدیل را عمداً انجام می‌دهد. |
| کامیت‌ها در پروفایل گیت‌هابم دیده نمی‌شوند | ایمیل `user.email` با ایمیل حساب گیت‌هابتان یکی نیست. مرحلهٔ ۲ را اصلاح کنید (کامیت‌های قدیمی همان‌طور می‌مانند). |
| نشان (badge) بیلد در README قرمز/خاکستری است | ورک‌فلو یا شکست خورده یا هنوز اجرا نشده. تب **Actions** را ببینید. اگر نام مخزن یا نام کاربری با آدرس badge نمی‌خواند، آدرس‌ها را در README اصلاح کنید. |
| ورک‌فلوی Release شکست می‌خورد | معمولاً به این دلیل که نسخهٔ Tesseract روی سرور با آن‌چه پروژه آزموده تفاوت پیدا کرده. بخش ۹.۳ (انتشار دستی) را انجام دهید. |

### اگر خواستید چیزی را از تاریخچه پاک کنید

اگر تصادفاً فایلی حساس (مثلاً `settings.json` با کلید API) را کامیت **و push** کردید،
پاک کردنش در کامیت بعدی کافی نیست — در تاریخچه می‌ماند و قابل بازیابی است. در آن حالت:

۱. **فوراً** کلید API را در پنل همان سرویس باطل (revoke) کنید. این مهم‌ترین کار است.
۲. بعد سراغ پاک‌سازی تاریخچه بروید (ابزار `git filter-repo` یا حذف و ساخت دوبارهٔ مخزن).

## ۱۲. چک‌لیست امنیتی قبل از push

قبل از هر push — خصوصاً اولی — این‌ها را بررسی کنید. یک مخزن Public را همه می‌بینند و
هر چیزی که یک‌بار push شود، عملاً منتشر شده است.

- [ ] `git status` هیچ فایلی به اسم `settings.json` نشان نمی‌دهد.
- [ ] در هیچ فایلی کلید API، توکن یا رمز به‌صورت متن ثابت (hard-coded) نیست.
      برای بررسی: `git grep -in "sk-" ; git grep -in "api_key"` — خروجی نباید کلید واقعی داشته باشد.
- [ ] پوشهٔ `src/ScreenTextCopy/Tesseract/` نادیده گرفته شده (مرحلهٔ ۴).
- [ ] پوشه‌های `bin/`، `obj/` و `release/` نادیده گرفته شده‌اند.
- [ ] در اسکرین‌شات‌هایی که در README یا ایشوها می‌گذارید، کلید API، ایمیل یا نام
      دامنهٔ خصوصی دیده نمی‌شود.
- [ ] ایمیلی که در `user.email` گذاشته‌اید، همانی است که می‌خواهید عمومی باشد
      (وگرنه از ایمیل `noreply` گیت‌هاب استفاده کنید).

> کلید API کاربران در `%AppData%\ScreenTextCopy\settings.json` روی رایانهٔ خودشان ذخیره
> می‌شود و **رمزنگاری‌شده نیست**. این موضوع در `SECURITY.md` صریح نوشته شده است. آن
> فایل هیچ‌وقت بخشی از مخزن نیست.

|---|---|
